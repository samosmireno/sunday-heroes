# Operations and hosting

_Branch session 14, 2026-09-16. Output of the fifteenth `/grill-with-docs` session for the rewrite. Takes `00-map.md` and `12-architecture.md` as settled; settles the open questions under area 14 of the map and records the proposals put to the user, accepted and declined. Nothing here is code, and nothing here is an ADR: every choice in this document is reversible by a blueprint change and a DNS record, which is the point of choosing it._

## Purpose

Run the thing safely: deploy, migrate, watch, back up, schedule. The architecture session fixed the shape of what runs, one image as two long-lived commands beside one Postgres, and what the code emits, request ids, one log line per act, one error hook, `/health` with the build id. This session picks where that runs, how a commit becomes a release, what proves a migration before production sees it, where the backups go and who checks that they restore, which vendor holds the errors and the heartbeats, what an alert is, and what it all costs. It also gives the app the two operational surfaces it lacked: a read-only mode for cut-over and restores, and a System page for the Operator.

## What today does, as evidence

Facts found in the current repository and the current host during this session that shaped a decision. None of them carries over.

- **Production is Render, Frankfurt**: one Docker web service on the Starter plan, one instance, no health check path, auto-deploying every commit on `main`; a Postgres 17 instance on the Basic-256 MB plan with 5 GB of disk, no connection pool, and an IP allowlist of `0.0.0.0/0`. About $13 a month.
- **The push is the release.** The image's start command runs the migrations and then the server, so a migration on `main` is in production minutes after the push. The 2026-09-03 Season migration was live before its rehearsal ran. CI runs lint, format, types and tests and never builds or deploys, and the Docker build type-checks files CI does not, so a green CI has broken a deploy.
- **Nothing watches it.** No error tracking, no uptime check, no heartbeat on the two in-process crons; a stopped cron is noticed when a vote fails to close. Logs are read by paging the host's CLI and stitching pino-pretty records back together.
- **Backups are by hand.** Two production dumps sit at the repository root, gitignored; the rehearsal is a ritual in the README, run after the fact; nothing has ever been restored from the host's own snapshots.
- **The developer `.env` holds the production database URL**, which is why `migrate:dev` needed a localhost guard, and a second copy of the production secrets sits in a root `.env` nothing loads. The local files also still name a Vercel host that has been dead since before September.
- **The compose file runs Postgres 16; production runs 17.**
- **The domain is in order.** `sunday-heroes.app` is at Porkbun with `www` canonical and the apex redirecting to it; Resend's DKIM, return-path and DMARC records are in place for the EU sending region, with inbound forwarding to a real mailbox, all recorded in `docs/email-deliverability.md`.
- **Test-error routes are mounted in production**, and the `render` CLI is logged in on the developer machine.

## The model

### Host and environments

**Render**, region Frankfurt for everything, one Project with two Environments. Nothing in the architecture is Render-specific: one image, Postgres, environment variables. The host scales the web service by plan and by instance count, the worker stays at one instance because pg-boss tolerates several anyway, and Postgres scales by plan up to read replicas and point-in-time recovery on the Pro tiers. If the user base grew a hundredfold, the first change would be a bigger Postgres plan and a cache behind one loader, as the architecture session foresaw, not a host move; and a host move is a blueprint rewrite and a DNS change.

| Environment    | Service  | Plan         | State                                              | Host                        |
| -------------- | -------- | ------------ | -------------------------------------------------- | --------------------------- |
| **production** | web      | Starter      | always on, one instance, health check on `/health` | `sunday-heroes.app`         |
|                | worker   | Starter      | always on, one instance                            |                             |
|                | Postgres | Basic-256 MB | always on, daily host snapshots                    | private network only        |
| **staging**    | web      | Starter      | **suspended by default**, resumed by the deploy    | `staging.sunday-heroes.app` |
|                | worker   | Starter      | suspended by default, resumed with the web         |                             |
|                | Postgres | Basic-256 MB | always on, because the rehearsal restores into it  | private network only        |

**The cost ceiling is about $25 a month**, and the arithmetic lands at $26:

| Item                                                  | A month           |
| ----------------------------------------------------- | ----------------- |
| Production web and worker, Starter                    | $14               |
| Production Postgres, Basic-256 MB                     | $6                |
| Staging Postgres, Basic-256 MB                        | $6                |
| Staging web and worker, billed per second while awake | cents             |
| Backblaze B2, Sentry, healthchecks.io, Renovate, GHCR | $0 at this volume |

`www.sunday-heroes.app` redirects to the apex, the reverse of today, so the share link read aloud at the pitch is the short one and every old link keeps working. Staging lives at `staging.sunday-heroes.app` with its own Google OAuth client in the same Google Cloud project, so a staging secret never opens production, and its own Resend sending domain, so its reputation is its own.

**Infrastructure is a file.** A `render.yaml` Blueprint in the repository declares both environments' services from the registry image, both Postgres instances, and one environment group per environment holding the non-secret configuration; every secret is marked `sync: false`, entered once in the dashboard and never written down. What a Blueprint cannot express, if the image-backed service or the pre-deploy command turns out to be one such field, is set by hand once and the deploy runbook says so.

### One image, six commands

One container image, built **once per commit in CI**, pushed to GitHub's container registry as `sha-<short sha>`, and pulled by every service of both environments; Render never builds. The build id the architecture puts on every response and in `/health` is that SHA, so "is the deploy live" is one comparison. The image runs as a non-root user on Node 22, contains the Postgres 17 client tools for the two commands that need them, and ships source maps to Sentry from the same CI job that built it.

| Command    | Runs as                              | Does                                                                                                                                                   |
| ---------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `server`   | a long-lived service                 | the tRPC router, the auth handler, the OAuth callback, the webhooks, the unsubscribe link, CSV, `/health`, the SPA                                     |
| `worker`   | a long-lived service                 | pg-boss's schedules and every job                                                                                                                      |
| `migrate`  | the web service's pre-deploy command | applies the committed SQL migrations and exits non-zero on failure, which aborts the deploy                                                            |
| `seed`     | a one-off job                        | builds the demo Group of the architecture session into an empty database                                                                               |
| `backup`   | a weekly pg-boss job in the worker   | `pg_dump` of the database to the off-host bucket, then a heartbeat ping                                                                                |
| `rehearse` | a one-off job on staging             | restores the latest dump into a scratch database on staging's Postgres, applies the migrations, runs the sanity check, drops it, then a heartbeat ping |

Settled in `15-migration.md`: a seventh command, `import-legacy`, runs once as a one-off job in the production environment on the Cut-over evening and is deleted from the image in the release after the Migration report is accepted.

### The release

The `deploy` workflow runs on every push to `main`, after the `check` job that is CI's gate:

1. Build the image once and push it as `sha-<short>`.
2. **Resume staging**, deploy the web service and then the worker by deploy hook with that image, wait for the health check, and verify that `/health` reports the SHA.
3. **Reseed staging** from the seed script, so nothing on it is ever precious and the next step is deterministic.
4. **The smoke**: one Playwright flow against staging, under a minute. Sign in with a seeded password Account, land on the Group home, open a match with an open Vote, cast a Ballot, see the Turnout change. The full suite already ran in CI against the same image; on staging the question is only whether the real host, database, secrets and OAuth client are wired, and one flow that crosses all four answers it.
5. **The gate**: if the release adds a migration file, trigger an extra backup of production, run the rehearsal (below), and wait for approval on the `production` GitHub Environment, one tap from a phone. If it adds none, continue without a pause. Continuous for the small fix, a pause for the schema change, no tags to remember.
6. **Deploy production, web first.** The web service's pre-deploy command runs `migrate`; a failure aborts the deploy and the old version keeps serving. Then the worker, so no job ever runs against a schema the migration has not reached. Then verify `/health`.
7. **Suspend staging** an hour later.

**Rollback is the same workflow dispatched by hand with a previous tag**, code only. That is possible because of one rule, checked in review and stated in `docs/ops/`: **expand and contract**. Every migration must be safe for the previous version to run against, because the previous version is what serves during the pre-deploy step and what a rollback restores. Adding a nullable column, a table or an index is one release; a rename or a drop is two, the first adding and writing both, the second removing the old once nothing reads it. A football app can wait one release to drop a column, and it turns a rollback from a restore into a redeploy.

### The rehearsal

The migration rehearsal stops being a ritual and becomes a job. `rehearse` runs as a one-off job in the staging environment, started by the deploy workflow whenever a release carries a migration and by a weekly schedule regardless. It downloads the latest dump from the bucket, restores it into a scratch database on staging's Postgres, applies the migrations from the image about to be released, runs a sanity check, row counts per table against the manifest the backup wrote beside the dump and one engine read per module over the restored data, drops the scratch database, and pings its heartbeat. The weekly run without any migration is what proves, every week, that the backup restores.

### Backups

Three layers, each covering the one above it:

1. **The host's daily snapshots** of the production Postgres, kept about a week on the Basic plan; point-in-time recovery is a Pro-tier feature and is not bought.
2. **A weekly off-host dump** by the `backup` job in the production worker, early Monday morning in the Group's part of the world after the Sunday matches, to a **Backblaze B2** bucket outside the host's account, kept eight weeks, plus an extra run before every release that carries a migration. Ballots are the one thing that can never be re-entered, and one host account is one failure domain.
3. **The weekly rehearsal**, which restores the newest dump and so turns "we have backups" into "we restored one on Monday".

Only the database is backed up. Everything else is in git or in the Blueprint, and the secrets are re-entered from wherever you keep them. Settled in `15-migration.md`: the old app's final dump, taken on the Cut-over evening, sits under an `archive/` prefix outside the eight-week rotation and is kept indefinitely. The restore runbook covers the two cases: a restore into production's own instance from a host snapshot, and a rebuild on any Postgres from a B2 dump, with the app in read-only mode for the duration.

### Staging's mail

The architecture said Mailpit in every non-production environment, and that holds for the compose file and CI. On a hosted staging you want the verification link to reach your phone, so the rule gains one amendment: **a non-production environment sends real mail exactly when a recipient allowlist is configured.** Staging sends through Resend from `staging.sunday-heroes.app`; an address on the allowlist goes out; every other address, the seed script's fake ones included, is recorded as a Delivery marked **suppressed** and never sent. Production refuses to boot with an allowlist set, and no environment without one and without Mailpit can start either.

### Observability

The architecture fixed the seam; this session picks what sits behind it, on free tiers, two vendors:

- **Sentry** for errors on the server and in the browser, source maps uploaded by CI, PII off, no session replay, no performance tracing, the request id as a tag so an error and its act log line meet. Its one free uptime monitor watches `/health`.
- **healthchecks.io** for heartbeats, which is what it is built for: four checks, each pinged at the end of a successful run and alerting when the ping is late. The **deadline close**, every few minutes, so a stopped scheduler is noticed within ten; the **hourly sweep**; the **backup**; the **rehearsal**.
- **Render's own logs** for the pino JSON lines, retention about a week, read through the CLI as today. A transport to a log vendor is one file behind the seam if a week ever turns out too short.

**Four alerts, and no others**, each to email and a phone app:

| Alert                     | Fires when                                                                    | Source          |
| ------------------------- | ----------------------------------------------------------------------------- | --------------- |
| the app is down           | `/health` fails for three minutes                                             | Sentry uptime   |
| the schedules stopped     | the deadline-close or the hourly-sweep heartbeat is late                      | healthchecks.io |
| something new is broken   | the first occurrence of a new error issue, never a count threshold            | Sentry          |
| the safety net has a hole | the backup or the rehearsal heartbeat is late, or either job reported failure | healthchecks.io |

Nothing on latency, traffic or disk. Alerts you learn to ignore are worse than none; each of these means something is actually broken for the group on Sunday.

**What never enters a log.** pino redacts email addresses, tokens, cookies, the `Authorization` header and passwords by path; a request line carries the request id and the Account id, never the email; the browser SDK sends no user email. The security events table keeps the IP and user agent as the identity session settled; the logs do not need them. The Operator's Account section is where a person is looked up by email; the logs answer "what did this request do", keyed by the id Sentry and the act log line share.

### The database's network and version

The production Postgres allows no address from the internet: the allowlist is empty, the app and the worker use the internal URL, the `backup` job uses a **read-only role**, and when you need `psql` from a laptop you add your current IP for the afternoon and remove it, or use the CLI's tunnel. A leaked URL is then a leaked string.

**Postgres 17 everywhere**: the compose file, CI's service container and both hosted instances run the same major, and bumping it is a deliberate act with its own rehearsal, like a migration. The connection budget stays inside the Basic plan's limit: a small pool for the server, a small pool for the worker, and pg-boss's own, added up in the typed configuration so a change is visible.

### Headers and transport

Render terminates TLS. The server sets on every response: HSTS with a one-year max-age; a Content Security Policy of `default-src 'self'`, with `connect-src` allowing Sentry and `img-src` allowing Google avatars; `X-Content-Type-Options: nosniff`; `Referrer-Policy: strict-origin-when-cross-origin`; a `Permissions-Policy` disabling camera, microphone and geolocation. The Vite build emits no inline scripts, so the policy needs no nonces. If Tailwind v4 or a Radix primitive turns out to inject an inline style, that one hash goes into the policy and `'unsafe-inline'` never does. The session cookie is `Secure`, `HttpOnly` and `SameSite=Lax`, which the auth library already sets.

### Shutdown and overlap

During a rollout the old and new instances overlap briefly and the host sends the old one SIGTERM. The server stops accepting connections, finishes in-flight requests within ten seconds, and exits. The worker stops fetching jobs, waits up to twenty seconds for running ones, and exits. Two workers alive at once need no guard: every job is idempotent on its record and pg-boss locks each job to one worker. The architecture already paid for idempotency; a deploy-time lock would be a second mechanism for a case the first one covers.

### Read-only mode

One configuration flag puts the whole app into **Read-only mode**: every act refuses with the `maintenance` reason, which the client renders as a banner on every screen; reads keep working; the worker pauses its schedules and its outbox. It exists for the cut-over of session 15, when the old app must be frozen and the new one verified before people are pointed at it, and for any restore. It costs one middleware and one banner, and the alternative is turning the app off.

### The System page

The identity session gives the Operator an Account section. This session adds one read-only **System page** under the same allowlist, a single `operator` read with no act on it: the build id and started-at of the web and the worker; the last run and outcome of every scheduled job; queue depth and failed jobs; the last backup and the last rehearsal with their outcomes; the count of Deliveries by outcome over the last week; whether Read-only mode is on. Everything the vendors know about "is it running", answered from inside the app; when something looks off at the pitch, this is the page to open before the host's dashboard.

### Dependency upgrades

**Renovate** through its GitHub app: exact pins; one pull request every Monday grouping every minor and patch, **auto-merged when CI is green**; one pull request per major, reviewed by hand; lockfile maintenance in the weekly group; the Docker base image and the GitHub Actions versions included. Auto-merge is what makes "weekly" survive a busy month.

### Runbooks and the repository

`docs/ops/` in the new repository, one short page each, written for an agent or a future you at ten on a Sunday night: **deploy** (what the workflow does and how to dispatch it by hand), **roll back** (a previous tag, and the expand-and-contract rule), **restore** (from a host snapshot, and from a B2 dump onto any Postgres, in Read-only mode), **rotate a secret** (each secret, where it lives, what to restart), **wake the worker** (a late heartbeat, the System page, resume or redeploy), **database access** (the temporary allowlist and the tunnel), **cut-over** (owned by session 15, outlined here and written in `15-migration.md`: the old app's `READ_ONLY` flag, the archive dump, the import under Read-only mode, the report, DNS, the point of no return, the decommissioning timeline), and **the cost sheet**. The `render.yaml` Blueprint sits at the root beside `compose.yml`.

## Scenarios that shaped the model

- **Sunday, 21:40, the worker dies quietly.** The last deadline-close ping was at 21:35; at 21:45 healthchecks.io marks the check late and the phone buzzes. The System page shows the worker's started-at from Sunday morning and no job run since 21:35. The wake-the-worker runbook says resume or redeploy; a redeploy by deploy hook takes two minutes. Votes read as closed when their deadline has passed whether or not the job stamped them, so nobody at the pitch noticed.
- **A migration that drops a column.** The release adds a column and writes both; CI is green; the workflow rehearses on Monday's dump, waits, is approved, deploys. The next week's release drops the old column. Had the first release dropped it, the previous version serving during the pre-deploy step would have failed on every read, and a rollback would have needed a restore.
- **The pre-deploy fails.** A migration hits a row that violates its new constraint. The `migrate` command exits non-zero, the host aborts the deploy, the old version keeps serving, Sentry has the error with the request id of nothing because it was a job, and the rehearsal that should have caught it is the thing to fix first.
- **Monday, the release is wrong.** Not a migration, a bug in Complete. The deploy workflow is dispatched with Sunday's tag; production runs the previous image against the same schema in three minutes. Nothing was restored.
- **The host account is lost.** Card declined, account suspended, region down, take your pick. The B2 bucket has eight Mondays of dumps and the repository has the Blueprint; a new Render account, or another host, runs the same image on a restored dump in an afternoon. The ballots are the only thing that could not have been re-entered, and they are in the bucket.
- **The seed script's addresses on staging.** The reseed on every deploy creates Accounts with fake addresses; the verification mails are recorded as suppressed Deliveries, the smoke's seeded Account is on the allowlist and its mail leaves, and nothing reaches a stranger.
- **Postgres 18 arrives.** The compose file, CI and the two instances move together, in one pull request with a rehearsal on a dump under the new major, never one at a time.
- **Renovate's Monday pull request fails CI.** It stays open, unmerged; nothing auto-merges on red. The failing package is pinned back or the fix is made, and the group's votes never met the broken version.
- **A leaked database URL.** It is in a screenshot. The allowlist is empty, so from anywhere but the host's private network it connects to nothing; the rotate-a-secret runbook rotates it anyway.
- **The cut-over.** Both apps in Read-only mode, the old one by its last deploy and the new one by its flag; the migration job runs; the report is read; the flag is cleared; DNS moves. The runbook outline is here, the job and the report are session 15's.

## Proposals

Put to the user as decisions, never adopted silently.

### Accepted

- **Render**, Frankfurt, one Project with production and staging Environments; a Starter web service, a Starter Background Worker and a Basic-256 MB Postgres per environment.
- **A cost ceiling of about $25 a month**, landing at $26 with staging's web and worker suspended between releases and its Postgres always on.
- **One persistent staging**, at `staging.sunday-heroes.app`, reseeded on every deploy, with its own OAuth client and sending domain.
- **A gated release**: `main` deploys to staging on every push; production follows automatically when no migration is present and after one approval when one is.
- **One image built once in CI** and pulled from GitHub's registry by every service; the build id is the commit SHA.
- **Expand and contract** as the migration rule, so a rollback is a previous tag.
- **The rehearsal as a job**: a one-off run on staging's Postgres from the latest dump, on every release with a migration and every week regardless.
- **Weekly off-host dumps to Backblaze B2**, eight weeks, plus one before every release with a migration, from a pg-boss job in the production worker.
- **Sentry** free for errors and the `/health` uptime monitor; **healthchecks.io** free for four heartbeats; logs left on the host.
- **Exactly four alerts.**
- **Staging sends real mail under a recipient allowlist**, recorded as the one amendment to the architecture's Mailpit rule; suppressed Deliveries for every other address.
- **Postgres 17 everywhere**, the major bumped as a rehearsed act.
- **An empty database allowlist**, the internal URL, a read-only backup role, a temporary allowlist entry for a laptop.
- **Renovate**, weekly minors and patches auto-merged on green, majors by hand.
- **Read-only mode** by one flag, with the `maintenance` refusal reason and a banner.
- **The Operator's System page**, one read, no acts.
- **A `render.yaml` Blueprint** with every secret `sync: false`, and **`docs/ops/` runbooks**.
- **The staging smoke** as one Playwright flow plus the build-id comparison.
- **The apex as the canonical host**, `www` redirecting.
- **Strict security headers** with a nonce-free CSP; a hash for any inline style the component library forces, never `'unsafe-inline'`.
- **Graceful shutdown rules** and no deploy-time lock on the worker.
- **Log redaction** of emails, tokens, cookies and passwords; the Account id, never the email, on a request line.

### Declined, and why

- **Fly.io, Railway, or a Hetzner box with Coolify or Kamal.** Fly's managed Postgres is new and pricier and everything else is more hands-on; Railway is Render's shape at usage prices with nothing already pointing at it; a VPS is cheapest and makes backups, Postgres upgrades and the worker's restarts your job, the opposite of "least ceremony". The DNS, OAuth client, Resend records and CLI already point at Render, and the map left hosting open only because the current setup misuses it.
- **A preview environment per pull request.** Cost per pull request, a fresh database and seed each time, and OAuth redirect URIs that multiply; the Playwright flows in CI already give every pull request a running app on a real database.
- **Continuous deployment to production with no gate**, and **tagged releases**. The first puts a migration in production on push, which is today's problem; the second is a tag to remember for every small fix. The gate that pauses only for migrations is both.
- **Letting the host build each service from the Dockerfile.** Two builds of one commit, twice the build minutes, and "one image" only by convention.
- **Breaking migrations with rollback by restore.** A restore under load on a Sunday night to undo a rename is the wrong trade for an app that can wait one release to drop a column.
- **A paid Sentry plan**, whose next tier alone would bust the ceiling; **Better Stack** for heartbeats and uptime, which would do the job with a nicer status view but is a second dashboard for the same four checks; **self-hosted GlitchTip**, a fourth service to run.
- **Shipping logs to a vendor** from day one. Logs were needed rarely today; the act log line plus Sentry's context cover the "what happened to Marko's ballot" question; a transport is one file later.
- **Alerts on latency, traffic, disk or error counts.** Each is an alert you learn to ignore.
- **Relying on the host's snapshots alone**, and **Cloudflare R2** for the off-host bucket, which would need a Cloudflare account that does not exist today; B2 is one signup and one bucket.
- **Mailpit as a private service on staging**, another paid service with no public URL; and **a staging that never sends**, which cannot test the one thing staging is for, the real verification link on a real phone.
- **Staging's Postgres on the free tier**, whose expiry terms would have to be verified and re-verified; **no staging worker**, which is how a worker bug reaches production first; **staging data kept between deploys** and **a copy of production data on staging**, since the rehearsal's scratch database already gives you production data when you need it.
- **Running the full end-to-end suite against staging.** It ran in CI against the same image; staging proves the wiring, not the app.
- **A Render cron job for the backup.** A third service with its own minimum charge for what a pg-boss job in the worker already does.
- **A deploy-time lock on the worker.** Idempotent jobs and pg-boss's job locks already cover the overlap.
- **Keeping `www` canonical.** The shorter host is the one read aloud.
- **Dependabot.** It would do, but Renovate's grouping, lockfile maintenance and pnpm support fit the weekly auto-merged group better.
- **A relaxed CSP with `'unsafe-inline'`**, and **logging the email for support convenience**; the Operator page is where a person is found by email.
- **Lighthouse in CI**, run by hand on staging instead; **a public status page**, since nobody outside the group is watching; **a CDN in front of the SPA**, since the host terminates TLS, the hashed assets cache long in the browser, and the group is in one city.
